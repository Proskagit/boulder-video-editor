### 2.2 Reproducibility of the zip (a possible improvement, not done)

The zip's **content** changes only with the recipe — between runs `39750948421` and `39755687421` the 18 files were
byte-identical except the manifests' toolchain image id; `fb3a252` added four licence files and extended the notices —
but the **zip's own SHA-256 changes with every run** (`9dd5d981…` → `ac751f05…` → `69afe49c…`): `zip -X -r` stores each file's
modification time, which is the time of that build, and the manifests carry the image id. A byte-reproducible zip would
need fixed timestamps for the files before packing (e.g. `touch -d @$SOURCE_DATE_EPOCH`, or a packer with a fixed
mtime and order) and a manifest without the per-run image id (or the image id kept out of the zip). Not changed: the
packaging and the build stay as they are until decided; the release takes the zip of one run as it is, with its hash.

Publishing steps (for later, on the product owner's command): download the artifacts of run `39770305364` again and
check them against the table, add the final 4, generate 8, create the annotated tag on `fb3a252`, create the release
with `--latest=false`, upload 1–8, download them back and check `SHA256SUMS` — before 2026-11-21 11:38 UTC, or repeat
the build (the binaries reproduce byte for byte; the zip's hash will differ, §2.2).

## 3. Independent check of the source set

**Done 2026-10-22: both binaries reproduced bit for bit** (details at the end of this section). Before it: the second
CI build ran only from the fetched sources (checked against `SHA256SUMS`, no network) and gave
the same bytes. What was missing: a rebuild from the tar alone, with the toolchain image rebuilt from scratch.

1. **A separate job or machine**, not reusing anything from run `39770305364`: a fresh GitHub-hosted runner of another
   image (e.g. `ubuntu-22.04` against the original `ubuntu-24.04`), or a Linux machine with Docker.
2. Download **only** `aive-ffmpeg-minimal-9.0.2-sources.tar`; check its SHA-256 against the release's `SHA256SUMS`.
3. Extract; check every file against the tar's own `SHA256SUMS`.
4. Build the toolchain image from `recipe/Dockerfile` with `--no-cache --pull` (the base image by digest, the packages
   from the snapshot); compare its `dpkg-query` list with `toolchainPackages` in `manifest.json`.
5. Run `recipe/build.sh` with `--network=none`, the extracted folder as `/sources` (read-only).
6. Compare `ffmpeg.exe` / `ffprobe.exe` with the published SHA-256. Equal: the source set is sufficient and the build
   reproducible across hosts. Different: compare `ffmpeg-configuration.txt`, `enabled-config.txt` and the toolchain list
   to find the cause; no publication until explained.
7. Optional: unpack the Debian source packages (`dpkg-source -x`) to show they are complete and match their `.dsc`
   checksums; rebuilding the toolchain itself from them is not planned (whether that is needed is part of the legal
   review).

The plan's estimate was one CI job of about 15 minutes; the run below took 4 minutes.

**Result** — workflow `.github/workflows/ffmpeg-minimal-rebuild.yml` (`c31a816`, fixed in `0976bb4`), run
[`39784758393`](https://github.com/Proskagit/boulder-video-editor/actions/runs/39784758393) at `0976bb4`, success,
2026-10-22 13:12–13:16 UTC. Steps 1–6 as above (step 7: below):
- a GitHub-hosted `ubuntu-22.04` runner (image `ubuntu22` `20261021.330.9`; the build job uses `ubuntu-24.04`), no
  checkout of the repository; only the artifact `ffmpeg-minimal-sources` of run `39770305364` downloaded;
- the tar 132 587 520 bytes, SHA-256 `4cafbbc6…d881` as expected; its `SHA256SUMS` 17 files OK; no build output in it;
- the toolchain image built from the tar's `recipe/Dockerfile` with `--no-cache --pull`: a new image id
  (`sha256:b88194ff…`, the source run's `sha256:8f104d19…`), snapshot `20261020T000000Z`, its 215 packages identical
  (name, version, source, source version) to `toolchainPackages` of the published `manifest.json`;
- `build.sh` of the tar with `--network=none`: `ffmpeg.exe` 17 416 704 bytes `9f51787f…3610` and `ffprobe.exe`
  17 206 784 bytes `2a1bf15f…5ab3` — **both MATCH** the published SHA-256; the rebuilt `manifest.json` differs from
  the published one only in the image id.

So this tar — the file §2 lists for the release, the same SHA-256 — is enough to rebuild the binaries on another host,
together with the toolchain image that its `recipe/Dockerfile` builds: the image build itself downloads the pinned
Debian base image (by digest) and the packages of the pinned snapshot; only `build.sh` runs without network. The
workflow uploads a report, the build log, the rebuilt manifest and the toolchain list (artifact
`ffmpeg-minimal-rebuild-report`, until 2026-11-21), never the binaries. It checked the tar of a CI run; a tar
downloaded from the published release would have to carry the same SHA-256 (§2's check after upload).

Found on the way (not a defect of the binaries): the sources tar is not byte-reproducible across runs. The build
of `c31a816` (run `39784008934`) gave the same binaries and notices but another tar (`bdc34560…9c36`): besides its
recipe, the git bundle of zimg differs in bytes (`b8563014…1170` against `b8f30307…7a4a`) for the same pinned commit
`67e06032…`. The release therefore takes the tar of run `39770305364` — the one rebuilt above.

Cause, checked locally on the two bundles (2026-10-22): the same bundle header (`pinned` = `67e06032…`), the same 14 168
objects (1 548 commits, tree `85508e42…`), the same `git archive` of the pinned commit and identical checked-out files —
the sources are the same. Only the packing differs: 10 369 against 10 366 objects stored as deltas, 113 objects with
another delta base. `fetch-sources.sh` makes the bundle from a fresh `git clone` of the upstream repository, and
`git bundle create` reuses the deltas of the pack the server sent — most likely what changed between the two clones (not
reproduced against the server: no network check was made). x264's and graphengine's bundles came out identical.
Re-bundling each through a fresh repository with `git repack -a -d -F` (`pack.threads=1`) gave the same bytes from both
(`02ca4fcc…`, 2 307 484 bytes) — a possible change of `fetch-sources.sh` to make the tar reproducible; not applied (it
would change the tar and require a new build and rebuild; the binaries are not affected).

**Product owner, 2026-10-22:** `fetch-sources.sh` is not changed for a byte-reproducible tar — the sources are the
same, only the Git packing differs; that the upstream server's pack is the cause is not confirmed.

**Step 7, 2026-10-22 — done locally with a stand-in for `dpkg-source -x`**, which is not available on the Windows
machine of the check (no dpkg, no WSL / Docker; nothing installed). On the Debian sources of the tar rebuilt above, in a
temporary folder, a script laid them out as `dpkg-source -x` does (3.0 (quilt): the orig tarball without its top
folder, `debian/` from the debian tarball, `debian/patches/series` applied with `patch -p1`; 3.0 (native): the one
tarball):
- `gcc-14` 14.2.0-19, 3.0 (quilt): both files match the `.dsc`'s SHA-256; unpacked (276 files); no
  `debian/patches/series`, so `dpkg-source` applies no patch (GCC's patches are applied by `debian/rules` at build
  time). The upstream sources inside the orig tarball read to the end: `gcc-14.2.0-dfsg.tar.xz` (140 408 entries, with
  the `COPYING.RUNTIME` and `COPYING3` that the zip carries) and `newlib-4.4.0.20231231.tar.xz` (5 843 entries).
- `gcc-mingw-w64` 27, 3.0 (native): the file matches the `.dsc`; unpacked (145 files).
- `mingw-w64` 12.0.0-5, 3.0 (quilt): the three files (orig, its upstream signature `.asc`, debian) match the `.dsc`;
  unpacked (6 639 files); the 7 patches of `debian/patches/series` applied cleanly.
- In every archive: no absolute or `..` path, no link, no name differing only in case. No problem found.

Not checked: the `.dsc` signatures (keys `D56571B8…A6F5` for gcc-14, `9CF557FE…839C` for gcc-mingw-w64 and mingw-w64)
and the upstream signature of the mingw-w64 tarball (`CAF5641F…C740`) — no Debian keyring here. The files' authenticity
rests on `apt-get source` in `fetch-sources.sh` (the snapshot's signed index, checked by apt in the image) and on the
tar's SHA-256. It is not `dpkg-source` itself; running it (e.g. in the toolchain image) would confirm the same.

> **Minimal FFmpeg 9.0.2 for AiVideoEditor — build 1 (win64)**
>

> No network, no other external libraries.
>
> - `ffmpeg.exe` 17 416 704 bytes, SHA-256 `9f51787f…3610`; `ffprobe.exe` 17 206 784 bytes, SHA-256 `2a1bf15f…5ab3`.

>   Patent License 1.0 and the Independent JPEG Group's terms (this software is based in part on the work of the
>   Independent JPEG Group).
> - Licence: GPL version 2 or later (FFmpeg with x264); see `THIRD-PARTY-NOTICES.txt`. Complete corresponding source:
>   `aive-ffmpeg-minimal-9.0.2-sources.tar`; see `SOURCE-OFFER.txt`.
