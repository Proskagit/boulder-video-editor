## 1. Продуктовая цель и подтверждённые ограничения

**Цель (владелец, 2026-11-04).** Отслеживать движение камеры относительно стены и пересчитывать координаты уже
расставленных зацепок, чтобы контуры оставались на своих физических местах при движении, повороте и дрожании камеры.

Основной сценарий:
1. Пользователь расставляет зацепки.
2. Система оценивает движение изображения между кадрами.
3. Координаты зацепок корректируются с учётом движения камеры.
4. При воспроизведении и экспорте зацепки остаются на своих местах стены.
5. При ненадёжном трекинге система не выдаёт незаметно неправильные координаты.
6. Ручная коррекция через keyframes — если её предусматривает архитектура.

**Вне границ:** трекинг спортсмена и произвольных объектов, привязка текста и подписей к объектам, универсальные
пространственные якоря, распознавание маршрутов, функции, не связанные с компенсацией движения камеры.

**Согласование с прежними решениями.** Цель совпадает с E из `docs/DEVELOPMENT_PLAN.md` (три пункта: контуры следуют
за камерой одинаково в Preview и экспорте; ручная коррекция при ошибке трекинга; анимация D036 поверх) и с решением R-6.
R-6 требует:
- компенсация действует во всём окне показа контуров;
- сначала модель similarity, гомография — при нехватке точности;
- «заведомо смещённые контуры не показываются как корректные».

Пункт 5 цели — это и есть требование R-6.

**Происхождение упомянутых ранее критериев:**

## 2. Карта текущей реализации

Весь код написан на C#, без новых зависимостей; формат `project.json` не затронут.

| Компонент | Файл | Роль |
|---|---|---|
| `WallTransform` | `src/Core/Motion/WallTransform.cs` | Проективное преобразование 3 × 3 нормализованных координат; композиция, обращение, линейная интерполяция |
| `CameraMotionTrack` | `src/Core/Motion/CameraMotionTrack.cs` | Выборки «время источника (тики) → преобразование опорный кадр → кадр + надёжность». Возвращает одно из трёх: `Aligned`, `Hidden`, `NoData`. Смешивает две надёжные выборки, если между ними ≤ 0,25 с. `Map(markedAt, t) = T(t) · T(marked)⁻¹` |
| `CameraMotionEstimator` | `src/Core/Motion/CameraMotionEstimator.cs` | Углы Shi–Tomasi опорного кадра и пирамидальный Lucas–Kanade **от опорного кадра**; предыдущая оценка служит только начальным приближением. При потере трека — грубый поиск сдвига, затем зума. RANSAC для similarity и гомографии (спортсмен отбрасывается как выброс). Модель выбирается на весь клип: similarity, если она укладывается в 3 / 6 px на **всех** кадрах, иначе гомография. Кадр надёжен при ≥ 30 инлаеров, ≥ 30 % отслеженных точек и модели в пределах 3 / 6 px |
| `FeatureTracker`, `GrayImage`, `CameraMotionMath` | `src/Core/Motion/` | Углы, пирамиды, LK, грубый поиск; фиттинг и RANSAC с фиксированным seed (детерминизм) |
| `CameraMotionRange` | `src/Core/Motion/CameraMotionRange.cs` | Окно анализа: с анимацией D036 — от её начала до исчезновения контуров, без анимации — **весь диапазон источника клипа**. Окно расширяется до времени разметки каждой зацепки; опорный кадр — кадр разметки первой зацепки |
| `CameraMotionCoordinator` | `src/UI/Services/CameraMotionCoordinator.cs` | Фоновый анализ всех клипов с зацепками, по одному за раз. Программное декодирование в 960 px с правилом HDR D033, выборка раз в **0,1 с**. Кэш в памяти по ключу «файл + окно + опорный кадр». Отдаёт `Tracks` для Preview и `ForExport()` для экспорта |
| Отрисовка | `CompositionDrawPlan.Outline(…, frameTimestamp)` | Каждый контур переносится по **PTS показанного кадра**. `Hidden` — контур не рисуется; `NoData` — рисуется на месте разметки. Preview (`PreviewDrawPlan`) и экспорт (`LayerOperations`) используют одну функцию |
| Экспорт | `ExportPreflight.CheckHoldTracking` | Блокирует экспорт (`HoldTrackingPending`), пока анализ клипа идёт. На **сбой** анализа не реагирует |
| UI | `HoldMarkupViewModel.Tracking.cs` | Статус в Inspector («привязываются», «привязаны», «привязаны; на N % кадров скрыты», «не удалось», «выключено»), переключатель «Следовать за камерой» и команда «Повторить». Состояние сеанса: не шаг Undo и не сохраняется |

**Поток данных:**
1. Holds клипа и `CameraMotionRange` дают окно анализа.
2. `CameraMotionCoordinator` декодирует 960 px, раз в 0,1 с передаёт кадры в `CameraMotionEstimator` и получает `CameraMotionTrack`.
3. `PlaybackSnapshotBuilder.Build(project, version, motion)` кладёт трек в `HoldOutline.Motion`.
4. `CompositionDrawPlan.Outline` переносит контур по PTS кадра — одинаково для Preview и экспорта.

**Как обрабатываются виды движения [Код]:**
- **Панорамирование и наклон** — гомография плоскости стены.
- **Поворот и зум** — similarity или гомография; смена объектива — через грубый поиск зума.
- **Дрожание** — только в пределах выборки раз в 0,1 с: между выборками преобразование интерполируется линейно, а колебания быстрее ~5 Гц не наблюдаются (см. дефект Д1).

**Дрейф.** Каждый кадр сопоставляется с **опорным** кадром, а не с предыдущим. Поэтому ошибка не накапливается по цепочке
по построению. На длинных дистанциях риск другой: изображение всё больше отличается от опорного, и падает число
сопоставлений.

## 6. Дефекты и ограничения

### Д1. Быстрое движение между выборками: контур на 0,1–0,15 с уходит с зацепки, а кадр считается надёжным *(обязательно для цели)*

- **Сценарий:** камера резко дёргается (толчок штатива, рука) быстрее, чем раз в 0,1 с.
- **Ожидаемое поведение:** контур остаётся на зацепке или скрывается (R-6, пункт 5 цели).
- **Фактическое поведение:**
  - Анализ берёт кадр раз в 0,1 с, `CameraMotionTrack.At` линейно смешивает соседние выборки.
  - Если движение между ними нелинейно, контур на промежуточных кадрах показан со смещением.
  - В том числе **до** начала рывка: интерполяция «предвосхищает» движение, которого ещё нет.
- **Доказательства [Реальные данные]:**
  - Клип 110133, 6,44–6,58 с: ошибка 13–35 px (медиана), без трекинга 2–100 px. Через 0,2 с снова < 2 px.
  - HDR-пилот, 1,40–1,54 с: 7–66 px.
  - Увеличенные фрагменты подтверждают визуально: в момент рывка крест сдвинут примерно на 30 px от края зацепки, после рывка — на месте.
  - Частота: 102 интервала с движением > 20 px между соседними выборками на ≈ 40 мин видео (≈ 10 с суммарно). На клипах со штативом их почти нет.
- **Влияние на пользователя:** редкий, но заметный «прыжок» контура на несколько кадров — в Preview и в экспорте.
- **Исправление:** адаптивная плотность анализа.
  - Если смещение углов кадра между соседними выборками превышает порог (например, 8 px при 1920), проанализировать все кадры между ними.
  - Или помечать такой промежуток `Hidden`, если плотный анализ не удался.
  - Цена — время анализа только на участках рывков.

### Д2. Надёжность кадра оценивается самосогласованностью: на смазанных кадрах и съёмке с рук настоящая ошибка выше показанной *(обязательно)*

- **Сценарий:** сильная смазанность при быстрой панораме или съёмка с рук.
- **Ожидаемое поведение:** кадр с ошибкой выше порога помечается ненадёжным.
- **Фактическое поведение:**
  - Надёжность считается по остатку модели на её же инлаерах (≈ 1 px).
  - Независимая ошибка на 103744 (116–117 с, сдвиг ≈ 766 px) — 2–5,5 px медиана: 11 из 21 момента выше гипотезы 3 / 6 px.
  - На 104651 (с рук) около опорного кадра: 4 из 5 «надёжных» моментов выше порога, до 20 px (7,0 с).
- **Доказательства:** `validate.py` (SIFT-соответствия как эталон) — раздел 7.
- **Влияние:**
  - На штативных клипах — порядка ширины штриха, малозаметно.
  - На клипе с рук — заметные кадры с контуром мимо зацепки.
- **Исправление:**
  - Добавить к критерию надёжности независимую проверку: например, сопоставление в обратную сторону или ограничение на скорость движения и смазанность.
  - После согласования D-15 проверять порог независимым инструментом из этого аудита.

### Д3. Сбой анализа или почти полностью ненадёжный трек — контуры молча выводятся без привязки (сбой) или почти весь клип скрыты, а экспорт об этом не сообщает *(обязательно)*

- **Сценарий:**
  - Анализ клипа упал (ошибка декодера, занятый файл).
  - Или трек почти целиком ненадёжен: на 104651 — 1520 из 1539 выборок.
- **Ожидаемое поведение (R-6, пункт 5 цели):** пользователь явно видит, что контуры не привязаны, и экспорт не выдаёт смещённые контуры незаметно.
- **Фактическое поведение [Код, Тест]:**
  - При сбое контуры рисуются на месте разметки (`NoData` → «как без трекинга») и в Preview, и в экспорте. Об этом сообщает только Inspector, и только у выбранного клипа.
  - `ExportPreflight.CheckHoldTracking` проверяет только `Pending`. Поведение закреплено тестом `A_failing_decoder_leaves_the_contours_untracked`.
  - Почти полностью ненадёжный трек получает статус «привязаны; на 99 % кадров скрыты», и контуры клипа практически не видны. Это не ошибка положения, но и не явная неудача (предложение 6.6 п. 3 не реализовано).
- **Влияние:**
  - Экспорт клипа с движущейся камерой после сбоя содержит контуры мимо зацепок — до 128 px в окне исследования, до сотен пикселей на длинных клипах.
  - Пользователь узнаёт об этом, только если выделит клип.
- **Исправление (поведение выбирает владелец, D-9 / D-13):**
  - Предупреждение или блокировка в preflight для клипов со сбоем анализа и с долей ненадёжных кадров выше порога.
  - Состояние «не удалось» при такой доле.
  - По умолчанию — не показывать непривязанные контуры клипа с движением после сбоя, пока пользователь явно не выключит привязку.

### Д4. Нет сохранения: повторный анализ при каждом открытии и при каждом изменении окна *(полезное улучшение)*

- **Сценарий:** открыть проект, обрезать клип или сдвинуть начало анимации.
- **Фактическое поведение [Код]:**
  - Трек живёт только в памяти. Ключ кэша включает окно анализа, поэтому trim или slip клипа без анимации меняет окно и запускает полный пересчёт.
  - Экспорт до конца анализа заблокирован.
  - `_results` не очищается в течение сеанса (рост памяти небольшой).
- **Влияние:** см. раздел 8 — для клипа без анимации длиной 10 мин это ≈ 160 с ожидания после каждого открытия.
- **Исправление:**
  - Хранить трек как производные данные в кэше проекта, по образцу миниатюр (`ProjectCacheFolder`), без изменения `project.json`.
  - Анализировать только недостающую часть окна.

### Д5. Ручная коррекция минимальна *(требует решения владельца)*

- **Есть:** «Следовать за камерой» вкл./выкл. и «Повторить» — только на весь клип и только на сеанс.
- **Нет:** исправления отдельного участка, keyframes, сохранения.
- По решению D048 §1.17 этого достаточно для продолжения; для «завершения E» вопрос открыт.

### Д6. Скрытие без затухания *(полезное улучшение)*

- Контур появляется и исчезает резко (6.6 предлагал затухание, D-9).
- На реальных треках переключений мало: на 104651 — 4 за 179 с. Мерцание не наблюдалось, но резкое исчезновение остаётся.

### Ограничения (не дефекты)

- Модель плоская: контур на объёмах (непланарных) переносится по плоскости стены. Независимая ошибка на точках объёмов выше.
- Анализ в 960 px: предел точности ~1 px в масштабе 1920.
- Если кадр разметки какой-либо зацепки ненадёжен, `Map` возвращает `Hidden` — эта зацепка не показывается во всём клипе [Код]. Обычно все зацепки размечаются на одном чистом кадре, поэтому на практике это редкость.

## 9. Keyframes и ручная коррекция

- **Есть [Код, Тест]:**
  - «Следовать за камерой» — выключает трек клипа, контуры остаются на месте разметки и в Preview, и в экспорте;
  - «Повторить» — после сбоя.
  - Оба действия — состояние сеанса: не шаг Undo, не сохраняются; новый проект включает трек обратно.
- **Нет:**
  - keyframes, исправление отдельного участка, сдвиг или поворот контура на кадре с переносом на соседние кадры;
  - сохранение коррекции.
- **Архитектура:**
  - Трек — неизменяемые данные по времени источника, применяемые в одной функции отрисовки. Keyframe-коррекцию можно
    наложить как дополнительное преобразование `T_corr(t)` поверх `T(t)` с интерполяцией между ключами.
  - Но ключи — это данные пользователя: им нужно место в проекте (новая версия формата, сейчас v13) и шаги Undo. Это
    вопрос D-7, его решает владелец.
- **Решение владельца 2026-10-27 (D048 §1.17):** текущей коррекции достаточно для продолжения, расширенная — отложена.

## 10. Окклюзия зацепок спортсменом (отдельно)

Желаемое поведение: контур зацепки, закрытой телом спортсмена, рисуется **под** спортсменом, то есть закрытые участки
контура не видны.

1. **Была ли частью замысла.** Да, частью **исходной концепции R2** (владелец, 2026-10-22, `docs/DEVELOPMENT_PLAN.md`,
   «R2 → E»): «Occlusion hides only the covered segments of the contour…». Также в ROADMAP, строка R2: «…with occlusion
   that hides only the covered segments». Однако решением **R-7 (2026-10-26)** окклюзия вынесена в **отдельный будущий
   этап**, не смешивается с компенсацией камеры и **не входит в три пункта E**.
2. **Упоминания:**
   - `PHASE_HOLD_TRACKING.md` — 1.2, 1.3 (T3), 2.1 (W11, W12 — «необязательно для MVP»), 7 (постановка, подходы, эксперимент, статус), 13.3;
   - `docs/DEVELOPMENT_PLAN.md`, «R2 → E» (концепция; «Occlusion was part of the R2 concept, not of E's three points»);
   - `ARCHITECTURE.md` («Occlusion is not part of it»);
   - `docs/TARGET_WORKFLOW.md` («отдельный будущий этап»);
   - DECISIONS.md — D045, D046 §9 и D047 (вне границ Phases 29–31).
3. **Реализация или задел [Код].** Реализации нет. Задел:
   - трек T2 (нужен, чтобы знать, где контур на кадре t);
   - опорный «чистый» кадр;
   - модель SAM 2.1 в проекте;
   - прозрачность по полигонам в плане отрисовки (`PolygonOpacities`) — но **по целым контурам, не по участкам**.
   - Отрисовщик рисует контуры замкнутыми полилиниями; скрытие участков потребует отрисовки открытых сегментов.
4. **Способы в текущей архитектуре:**
   - (а) **разность с выровненным чистым кадром в полосе вокруг контура** — нормализация экспозиции, временной гистерезис;
     без новой модели. В эксперименте 2026-10-26 качественно выделяла спортсмена (3–4 % пикселей), но только при
     выравнивании T2; точность границы и мерцание не измерялись;
   - (б) **сегментация человека** отдельной ONNX-моделью — новая зависимость, лицензия, размер;
   - (в) **SAM по спортсмену** на каждом кадре — 0,35 с на GPU / 7,4 с на CPU на кадр, слишком медленно для всего окна.
   - Результат (видимые участки по времени источника) считается заранее, как трек, и применяется в той же функции
     отрисовки — паритет Preview / экспорт сохраняется.
5. **Нужна ли сегментация.** Нужна какая-то оценка перекрытия: маска разности (а) или маска человека (б / в).
6. **Производительность и качество:**
   - Перекрытие меняется быстро, поэтому анализ нужен на каждом кадре окна показа (255–510 кадров на окно 8,5 с), а не раз в 0,1 с.
   - (а) — единицы миллисекунд на кадр в низком разрешении; (б) — десятки миллисекунд на GPU, больше на CPU.
   - В Preview и экспорте — только применение заранее посчитанных данных.
   - Риски качества: мерцание на краях, тени, магнезия, похожий цвет одежды и зацепок. Для приёмки нужна ручная разметка силуэтов.
7. **Независимость от компенсации камеры.** Частичная:
   - на неподвижной камере окклюзию можно считать без T2;
   - при движении камеры видимые участки определяются в позиции контура на кадре t, то есть по данным T2;
   - для подхода (а) T2 обязателен и для самой маски.
8. **Сложность.** Выше основной задачи. T2 уже работает с точностью ~1 px; окклюзии нужны новая оценка перекрытия,
   отрисовка по участкам, хранение видимости, борьба с мерцанием и эталон для приёмки.

**Вывод по окклюзии:** **предусмотрена исходной концепцией R2, но решением R-7 вынесена в отдельный будущий этап; не
реализована, есть частичный задел (T2, чистый кадр, общий путь отрисовки); технически возможна в текущей архитектуре;
требует отдельного решения владельца** — подход (а / б), формат хранения, приёмка. В завершение E не включается.
