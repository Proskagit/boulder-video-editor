## 0. Что изменилось в ревизии 2

1. **Два понятия разведены везде:** *цвет зацепов трассы* (ЧТО выделять — набор зацепов) и *цвет обводки* (КАК
   выделять). Цвет обводки выбирает существующий `RouteColor` — он переиспользуется без нового алгоритма (3.2, 8.2).
   В ревизии 1 эти понятия местами смешивались (`RouteColorEstimator`) — исправлено.
2. **Три варианта определения набора** — A (полностью автоматически), B (одна контрольная зацепка), C (контрольная
   зацепка + анализ видео) — сравнены по существу и экспериментально (5, 10.2). Контрольная зацепка рассматривается как
   полноценный кандидат на MVP, а не обходной путь.
3. **Tracking пересмотрен:** компенсация движения камеры нужна во всём окне видимости контуров, а не только при
   пересечении анимации со скалолазом. «Сдвиг анимации, чтобы она закончилась до появления скалолаза» больше **не**
   предлагается как замена компенсации (в ревизии 1 он был ключевым предложением MVP — снято). Критерий X3 переписан:
   решает измеренное движение камеры в окне видимости контуров (6, 10.3).
4. **Occlusion отделён** от компенсации движения и может быть отложен (7).
5. **Формат проекта:** решение о `project.json` v10 **не принимается**; требования к сохранению — открытый вопрос (8.5,
   14.3). В ревизии 1 v10 был рекомендацией — снято.
6. Пороги ревизии 1 (recall ≥ 85 %, precision ≥ 70 %, ошибка позиции ≤ 2 / 4 px и др.) не были проверены; они заменены
   измеренными базовыми линиями и рабочими гипотезами (13), с объяснением.
7. Добавлены исследовательские скрипты `tools/hold-tracking-research/` (вне решения; не продуктовый код).

## 1. Цель, понятия и границы

### 1.1. Цель

Довести автоматическую разметку болдер-трассы до сценария владельца: на чистом кадре стены сформировать **полный набор
зацепов трассы** (включая те, которых скалолаз не касался), обвести их **контрастным цветом**, показать контуры во
вступительной анимации снизу вверх (~5 с) и держать контуры **на физических зацепах** всё время, пока они видны, даже
если камера сместилась; по возможности не рисовать их поверх скалолаза.

### 1.2. Понятия (не смешивать)

| Понятие | Вопрос | Что определяет | Существующий код |
|---|---|---|---|
| **Цвет зацепов трассы** | ЧТО выделять | Какие зацепы принадлежат трассе (набор) | Нет |
| **Цвет обводки** | КАК выделять | Цвет линии контуров, контрастный к зацепам и стене | `RouteColor` (D034 §5) — есть [Факт] |
| **Компенсация движения камеры** | ГДЕ рисовать на кадре t | Преобразование «чистый кадр → кадр t» в окне видимости контуров | Нет |
| **Occlusion** | ЧТО из контура видно | Какие участки контура закрыты телом скалолаза | Нет |

Порядок: сначала набор зацепов трассы → затем цвет обводки по этому набору (`RouteColor`) → затем (при показе) где и
какие участки рисовать.

### 1.3. Задачи и варианты

- **T1. Набор зацепов трассы** — варианты: **A** полностью автоматический (цвет трассы по контактам рук и ног в видео
  пролаза — будущее исследование), **B** одна контрольная зацепка (**MVP**, R-1), **C** контрольная зацепка + видео как
  дополнительное свидетельство (**исключён из MVP**, R-4) (5).
- **T2. Компенсация движения камеры** — в окне, где контуры видимы; независима от способа T1; **в MVP** (R-6) (6).
- **T3. Occlusion** — отдельный будущий этап (R-7) (7).
- Цвет обводки — не отдельная задача: переиспользуется `RouteColor` (3.2).

### 1.4. Вне границ

- Восстановление последовательности зацепов по касаниям; автоопределение Top / Attempt; постоянная подсветка на всём
  пролазе (Сценарий §6).
- Трассы, размеченные тейпом при разноцветных зацепах (сценарий предполагает «одна трасса — один цвет»).
- Новые модели «на всякий случай» (поза, сегментация человека) — только если эксперимент покажет необходимость.
- Изменения Phase 31, Phase Coros, формата `project.json`, логики Undo — в этом задании не делаются.

### 3.2. `RouteColor` — цвет обводки, не цвет трассы

`src/Core/Entities/RouteColor.cs`:

- Палитра 14 цветов: 12 насыщенных (red, orange, yellow, lime, green, teal, cyan, blue, indigo, violet, magenta, pink),
  white, black.
- Оценка цвета c для зацепа i: `min(ΔE_OK(c, SurfaceLab_i), 2 · ΔE_OK(c, WallLab_i))` — стена с весом 0,5, потому что на
  ней лежит только внешняя половина линии. Оценка трассы — минимум по зацепам (худший случай).
- `Choose`: maximin по 12 насыщенным, если он достигает порога `KeylineThreshold = 0.16`; иначе лучший из white/black,
  если достигает; иначе maximin по всем 14 и включение keyline. Ничьи — большее среднее, затем порядок палитры.
- Пересчитывается только при изменении набора зацепов, из сохранённых сэмплов, **без декодирования кадров**.

**Вывод:** `RouteColor` решает ровно задачу «цвет обводки» и принимает на вход только набор `Hold` с `SurfaceLab` /
`WallLab`. Любой способ определения набора (A/B/C), который создаёт обычные `Hold` через существующий путь сэмплирования
(`HoldColorSampler`), автоматически получает правильный цвет обводки. **Нового алгоритма цвета обводки не требуется.**
[Измерено, иллюстративно] Копия правила `Choose` на Python (`tools/hold-tracking-research/outline_colour.py`) на наборах,
найденных вариантом B на двух клипах (кораллово-красная и синяя трассы), даёт lime, оценка трассы 0,38 / 0,48 (≥ 0,16 —
keyline не нужен).

**Цвета трассы в коде нет нигде:** ни `RouteColor`, ни `HoldColorSampler` не отвечают на вопрос «какие зацепы трассы».

## 5. Задача T1: набор зацепов трассы — варианты A / B / C

Общий конвейер для всех вариантов [Предложение]:

```
чистый кадр ─► кандидаты (SAM по промптам) ─► признаки кандидата (цвет поверхности / стены, размер, score)
            ─► эталон цвета трассы ─► отбор и ранжирование ─► ревью пользователя ─► обычные Hold (D034)
            ─► RouteColor (цвет обводки)
```

Варианты различаются **только источником эталона цвета трассы и дополнительными свидетельствами** — это и есть точка
расширения для W20.

### 5.1. Вариант A — полностью автоматический (будущее исследование, не MVP)

**[Решение владельца R-5]** Текущий прототип A не подходит, но и не доказывает, что A невозможен.

**Что было проверено и почему это не A.** Прототип ревизии 2 (10.2) считал «свидетельством» любой кандидат, который
**перекрывал силуэт скалолаза** хотя бы 1 с суммарно, и брал доминирующий цвет таких кандидатов. Силуэт перекрывает
зацепы туловищем, бёдрами и руками в движении, то есть любые зацепы на пути тела, в том числе чужих трасс. Поэтому на
обоих клипах первым выбран не цвет трассы (фиолетовый на 100405, красно-розовый на 103744). Это опровергает только
**постановку «перекрытие = свидетельство»**, а не идею автоматического определения.

**Правильная постановка будущего A** [Предложение для будущего исследования]:

- Свидетельство — **контакт конечности с зацепом**: кисть (и при необходимости стопа) находится на зацепе и неподвижна
  относительно стены в течение заметного времени (захват / постановка), а не «зацеп под телом».
- Пример: скалолаз держится руками за синие зацепы; ноги могут стоять на других зацепах или временно не касаться стены при
  перестановке. Вес рук должен быть выше веса ног; ноги могут подтверждать цвет, но не задавать его.
- Свидетельства **накапливаются по последовательности кадров**; цвет трассы — цвет, набравший устойчивое большинство
  контактов рук (с учётом длительности захвата). Кратковременное отсутствие видимого контакта (окклюзия, ракурс, переход
  между зацепами) — «нет данных», а не свидетельство против; оно не меняет текущую гипотезу.
- Решение выдаётся с уверенностью; при низкой уверенности — предложение пользователю, а не молчаливый выбор (см. 5.5).

**Что потребуется** (каждый пункт — отдельная оценка стоимости и лицензии): модель позы (ключевые точки кистей / стоп,
ONNX, вид со спины на стене, локально); выравнивание кадров пролаза с чистым кадром (переиспользует T2); связывание точки
конечности с маской кандидата на чистом кадре; детектор неподвижности конечности; временной накопитель свидетельств;
эталон владельца с отмеченными контактами для оценки.

**Статус:** отдельное исследование с дополнительной стоимостью; сейчас не реализуется, длительные эксперименты по нему не
запускаются; приоритет MVP — вариант B.

### 5.2. Вариант B — одна контрольная зацепка (основа MVP)

**[Решение владельца R-1]** Основной подход MVP. Результаты ниже — **предварительные** (R-2): два клипа одного зала,
разметка Claude, а не владельца; качество для всех трасс не подтверждено.

| | |
|---|---|
| Что реализуется | Клик пользователя по одной зацепке трассы на чистом кадре → маска SAM → цвет по **области** зацепки (эрозия, отброс 10 % тёмных / светлых, медиана OKLab, как `HoldColorSampler`) → карта цветового расстояния → промпты SAM в центрах «похожих» областей (+ при необходимости сетка) → маски по правилу D034 → цвет каждой маски → принятие при расстоянии < τ и score ≥ 0,5 → набор на ревью → пользователь удаляет лишние и добавляет пропущенные |
| Новые компоненты | Цветовая карта и размещение промптов (чистая функция на кадре); правило отбора; NMS (есть в Phase 31); UI: выбор контрольной зацепки (5.5), регулятор допуска, ревью (на базе Phase 31) |
| Не требуется | Модели позы, анализа видео пролаза, новых зависимостей; модель SAM та же |
| Что остаётся предположением | Что пороги (τ, score) переносятся на другие залы / свет; что пользователь быстро исправляет 4–6 ошибок (время коррекции не измерялось) |
| Предварительный результат | [Измерено, 2 клипа, разметка Claude] τ = 0,08, score ≥ 0,5, промпты «цвет + сетка 24×24»: precision 0,905 / 0,824, recall 0,826 / 0,933, F1 0,864 / 0,875, правок 6 / 4 (10.2). Пороги подобраны на первом клипе и применены ко второму без изменения |
| Ограничения (наблюдались) | Чувствительность к выбору контрольной зацепки (recall 0,65–0,87 и precision 0,48–1,00 при разных зацепках той же трассы); соседние цвета (коралловый / оранжевый / бордовый, синий / чёрный / фиолетовый); две трассы одного цвета на одной стене (метки TOP у двух синих зацепов) — цветом не различаются; фрагменты объёмов того же цвета как дубликаты |

Как помогает SAM [Измерено]: сетка Phase 31 без цвета даёт кандидаты всех цветов; **цветовые промпты** дают recall
0,78 / 0,87 при precision 0,93–0,95 за 37–192 промпта; сетка 24×24 только с цветовым фильтром — recall 0,65 / 0,73;
объединение — лучший recall (0,83 / 0,93) ценой ×3–4 времени. SAM отделяет зацеп от стены и от соседних зацепов (контур
по границе объекта), а не по цвету пикселя — поэтому порог применяется к цвету **маски**, а не пикселя.

Из наблюдённой чувствительности следует [Предложение]: регулятор допуска «похожесть цвета» в ревью (смена без
перекодирования кадра) и подсказка при выборе («крупная зацепка без бликов и мела»); несколько контрольных зацепок —
возможное расширение (14.3, D-3).

### 5.3. Вариант C — контрольная зацепка + анализ видео (исключён из MVP)

**[Решение владельца R-4]** C не входит в MVP и не планируется обязательным этапом.

| | |
|---|---|
| Что проверялось | B, плюс кандидаты в более широком цветовом окне (τ..τ_c), если скалолаз их перекрывал (выравнивание кадров пролаза, маска скалолаза разностью с чистым кадром) |

### 5.5. Выбор контрольной зацепки перед вступительной анимацией [Предложение UX]

**Требования (R-3):** до первого показа вступительной анимации у пользователя есть возможность выбрать контрольную
зацепку; без выбора система не угадывает трассу и не показывает случайные контуры; есть явное действие «выбрать /
пропустить / продолжить без контуров»; от пользователя не требуется успеть что-либо за 5 секунд.

**Ключевой принцип — выбор делается в режиме редактирования на паузе, а не во время воспроизведения.** Вступительная
анимация — свойство клипа на таймлайне (D036: её начало привязано ко времени источника), а не событие реального времени.
Пока набор зацепов не задан, анимации нечего показывать; поэтому её «первый запуск» — это первый показ после того, как
набор подтверждён. Никакого таймера и ожидания действия во время просмотра нет; Preview никогда не останавливается в
ожидании выбора.

**Простейший поток (одно место — раздел «Зацепы» в Inspector, существующий режим разметки D034):**

1. Пользователь выбирает видео-клип и ставит плейхед на чистый кадр (как сейчас). Если у клипа ещё нет зацепов, в разделе
   «Зацепы» видна строка-подсказка «Трасса не выбрана» и кнопка **«Выбрать трассу по зацепке»**.
2. Кнопка включает режим разметки с подсказкой в Preview: «Кликните одну зацепку трассы». Рядом две явные кнопки:
   **«Пропустить»** (вернуться позже) и **«Без контуров»** (этому клипу контуры не нужны).
3. Клик по зацепке → контрольная зацепка подсвечена → предложенный набор того же цвета на ревью (механизм Phase 31) с
   регулятором допуска → «Принять» (один шаг Undo) → обычные `Hold`, цвет обводки — `RouteColor`.
4. После принятия становится доступен блок «Анимация» (D036) — пользователь включает вступление; первый показ анимации
   уже с подтверждённым набором.

**Поведение без выбора:**

| Ситуация | Поведение |
|---|---|
| Пользователь ничего не выбрал и запустил воспроизведение / экспорт | Контуров нет (у клипа нет `Hold` — как сейчас, `HoldOutline` = null); анимация не играет; ничего не угадывается. В Inspector остаётся неблокирующая подсказка «Трасса не выбрана» |
| «Пропустить» | Режим разметки закрывается без изменений проекта; подсказка и кнопка остаются, к выбору можно вернуться в любой момент |
| «Без контуров» | Режим закрывается без изменений проекта; подсказка скрывается до конца сессии (как сохранять это намерение между сессиями — открытый вопрос, D-12) |
| Клик не дал маски (D034: все маски скрыты) | Сообщение «Не удалось выделить зацепку — кликните другую», режим остаётся открытым |
| Предложенный набор пуст или явно неверен | Пользователь меняет допуск, кликает другую контрольную зацепку или размечает вручную (D034); ничего не принимается без «Принять» |
| Набор принят, но в нём ошибки | Обычные правки: удалить зацеп, добавить кликом, поправить контур (D035) — анимация сразу отражает изменения |

**Взаимодействие с пятисекундной анимацией:** анимация показывает только подтверждённые зацепы и начинается с момента,
заданного на таймлайне (D036 `StartSourceTime`), независимо от того, когда пользователь сделал выбор. Если пользователь
передумал и удалил все зацепы — анимация снова пуста, без запасного «угаданного» набора. Экспорт без выбранной трассы —
допустим (без контуров); показывать ли предупреждение в preflight — открытый вопрос (D-13).

**Что сознательно не предлагается:** автоматический запуск выбора при открытии клипа (модальность мешает другим задачам);
автоматическая подстановка «самого вероятного» цвета; таймер.

## 6. Задача T2: компенсация движения камеры

### 6.1. Постановка (по уточнению W10′)

Для каждого кадра t окна видимости контуров найти преобразование T_t «нормализованные координаты чистого кадра →
кадр t». Окно видимости — из `HoldSchedule` (от `StartFrame` до `EndFrame`, или до конца клипа при
`StayUntilClipEnd`): при анимации 5 с + 3 с + 0,5 с это ≈ 8,5 с. Нужна **независимо** от того, есть ли скалолаз в кадре
и каким способом определён набор зацепов.

### 6.2. Последовательность моделей (от простой к сложной)

| Модель | Степени свободы | Когда достаточно | Стоимость |
|---|---|---|---|
| Без компенсации | 0 | Штатив, никто не трогал камеру | 0 |
| Сдвиг | 2 | Небольшое смещение без поворота / зума | Дёшево; можно фазовой корреляцией без зависимостей |
| Similarity (сдвиг + масштаб + поворот) | 4 | Поворот штатива, зум, стабилизация | Ключевые точки + RANSAC (или ECC) |
| Гомография | 8 | Заметный наклон / поворот относительно плоскости стены, съёмка с рук | Те же ключевые точки + RANSAC |
| Локальные поправки / плотный поток | много | Непланарные объёмы при сильном параллаксе | Заметно выше; не исследовалось |

### 6.3. Результаты измерений [Измерено, 10.3]

29 реальных клипов, окно 0,5–9,0 с от чистого кадра на 0,5 с (худшие по кадрам медиана / p95 ошибки, px кадра 1920):

- **Сессия 2026-09-27 (16 клипов, 4K, телефон на штативе / в руках):** без компенсации обходятся **2**; сдвига
  достаточно в **2**; similarity — в **6**; нужна гомография — в **6** (из них в 2 similarity на грани: медиана ≤ 3,2,
  p95 7,9–8,9). Смещение без компенсации до 117 px (медиана), до 2008 px в клипе с рук.
- **Чистый кадр после «успокоения» камеры (6 с), окно 6–14,5 с:** компенсация всё равно нужна в **13 из 16** (смещение
  без компенсации 7–134 px медиана); similarity достаточно для **13 из 16** (включая 3 без компенсации и 4 со сдвигом);
  гомография — для 3 (2 на грани, 1 клип с рук).
- **E1 (12 клипов со штатива, 10 с):** без компенсации 9, сдвига достаточно 3 — согласуется с E2.
- **HDR-пилот (с рук, стабилизация телефона):** смещение 320 px, similarity недостаточна (p95 41 px), гомография —
  1,8 / 3,7 px.
- Визуальная проверка (100405, контуры с 6 с на кадре 14 с): без компенсации контуры ≈ 20 px мимо зацепов; после
  similarity — на зацепах.

### 6.4. Решение и порядок проверки моделей

**[Решение владельца R-6]** Компенсация движения камеры входит в MVP и действует во всём окне показа контуров, в том
числе пока скалолаза ещё нет в кадре. Порядок: сначала similarity; если на соответствующих клипах её точности не хватает —
переход к гомографии; similarity **не** объявляется достаточной для всех роликов без проверки.

Детали ниже — **[Предложение]**:

1. Модель выбирается **по клипу и окну, по измерению, а не по умолчанию**: similarity по ключевым точкам с RANSAC
   (скалолаз отсекается как выбросы); если в окне её остаток на точках стены выше порога приемлемости (рабочая гипотеза
   3 / 6 px при 1920, ещё не согласована — 13.2) — гомография по тем же сопоставлениям; если и она не проходит — правило
   6.6. Эксперимент (10.3) показывает, что на материале владельца similarity хватает в 10–13 из 16 роликов, а не во
   всех: это аргумент за автоматический переход, а не за одну модель.
2. Сдвиг как самостоятельная модель не предлагается: в 11 из 16 клипов сессии (окно 0,5–9 с) его недостаточно.
3. Сглаживание траектории параметров (обработка офлайн, всё окно известно).
4. Плотный поток, SAM-пересегментация, SAM 2 video — по измерениям не нужны; не брать.
5. Реализация: своя на C# или OpenCvSharp4 — открытое решение (14.3, D-6).
6. Приёмка: на эталонном наборе роликов (штатив; поворот / зум штатива; стабилизация; с рук) остаток в окне не хуже
   согласованного порога, а кадры, где порог не достигнут, обработаны по 6.6 (11, S6–S7).

### 6.6. Если надёжно выровнять кадр не удалось

**[Решение владельца R-6]** Заведомо смещённые контуры не показываются как корректные. Как именно — [Предложение],
выбор за владельцем (14.3, D-9):

- **Признак ненадёжности кадра** (вычисляется при анализе): мало inliers; остаток выбранной модели выше порога;
  резкий скачок параметров относительно соседних кадров; кадр не декодирован / за пределами анализа.
- **Предлагаемое поведение (простейшее понятное):**
  1. Короткий провал (до ≈ 0,2 с) — интерполяция параметров между надёжными соседями (движение штатива плавное).
  2. Более длинный — контуры на этих кадрах **скрываются** короткой затухающей прозрачностью (без мерцания), а не рисуются
     на месте чистого кадра; после восстановления — плавно появляются.
  3. Если ненадёжна большая часть окна (например, съёмка с рук, 10.3: 35–50 из 85 кадров) — анализ считается неудачным:
     в Inspector сообщение «Не удалось привязать контуры к стене», контуры клипа не показываются в окне, пока пользователь
     не выберет: показать без привязки (явно, на свой риск), выбрать другой чистый кадр или отключить анимацию.
- Preview и экспорт ведут себя одинаково (одни данные, один путь отрисовки); предупреждение в preflight экспорта при
  частично скрытых контурах — открытый вопрос (D-13).
- Альтернативы для выбора владельцем: держать последнее надёжное преобразование ограниченное время; всегда рисовать без
  привязки с предупреждением (противоречит R-6 для экспорта — не рекомендуется).

### 6.5. Ограничения измерения

- «Истина» — сами сопоставленные точки стены (ORB-inliers гомографии с порогом 2 px на 960 px), то есть точки, которые
  гомография объясняет: ошибка гомографии на них занижена по построению; непланарные участки (объёмы) в оценку не
  попадают.

- Порог «достаточно» (медиана ≤ 3 px, p95 ≤ 6 px при 1920, ≈ одна ширина штриха по D034 §4) — рабочая гипотеза, не

## 7. Задача T3: occlusion

### 7.1. Постановка (W11, W12, концепция 2026-10-22)

Для кадра t и каждого зацепа определить участки контура T_t(`Points`), закрытые телом, и рисовать только открытые
участки собственного контура. Не рисовать по силуэту окклюдера, не скрывать весь контур из-за частичного перекрытия.

### 7.2. Подходы

| Подход | Суть | Плюсы | Минусы |
|---|---|---|---|
| Разность с чистым кадром после T2 | Чистый кадр, перенесённый T_t, сравнивается с кадром t | Чистый кадр уже есть (W4); без модели | Тени, экспозиция, параллакс |
| Разность только в полосе контура | То же для пикселей около контура | Дёшево; прямо отвечает на вопрос | Меньше контекста |
| Сегментация человека (ONNX) | Маска человека | Не зависит от чистого кадра | Новая модель, лицензия |
| SAM по скалолазу | Промпт на скалолаза | Точные края | Encoder на каждый кадр (0,35 с GPU / 7,4 с CPU) |

### 7.3. Что показал эксперимент (побочно, не метрика occlusion)

[Измерено, качественно] В анализе пролаза (эксперимент C и прототип «A по перекрытию», ревизия 2) разность с выровненным чистым кадром выделяла скалолаза
(3–4 % пикселей кадра на выровненных кадрах). Это работает только при трёх условиях: выравнивание (T2) — без него светятся
края всех зацепов; нормализация экспозиции (медианный сдвиг OKLab); допуск сдвига ±1 px анализа. Точность границы и
мерцание **не измерялись** (нужна ручная разметка силуэтов).

### 7.4. Статус

**[Решение владельца R-7]** Occlusion — отдельный будущий этап, не входит в MVP и не смешивается с компенсацией камеры:
данные, анализ и критерии T2 не зависят от T3. До его реализации контуры в окне показа рисуются поверх скалолаза, если он
там есть (как сейчас).

Для будущего этапа [Предложение]: основной вред (контуры мимо зацепов) устраняет T2; путь —
разность в полосе контура после T2 + временной гистерезис; хранение — открытый вопрос (маска низкого разрешения или
интервалы видимости; 14.3, D-8).
